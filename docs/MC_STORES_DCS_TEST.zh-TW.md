# MC 掛載觀測：必要 DCS 測試

目標：確認 DCS 實際提供哪些掛載／彈量欄位，並比對它們進入 MC 後的結果。
固定掛點、查詢、有效性、版本及事件的內部規則由自動測試驗證；本流程檢查遊戲介面與資料傳遞。

**執行版本：須使用包含 StoresTelemetry 的新 Windows DLL，與本次 Lua 一起部署。
目前專案 bin 中的舊 DLL 尚未包含這些通道，本文件不是已完成建置的測試包。**

使用友軍機場的地面熱機停機位，機鼻朝空曠處；九掛點全空，機砲彈量 100%，無限彈藥關閉。
保存這份 `.miz`。整個流程在同一次任務中完成，每次地勤作業完成後保持正常運行 5 秒。

## 看哪裡

Debug Indicator 會顯示下列資料；同一份資料自動寫入安裝模組的 `log/debug.csv`。
工具原有操作項為 `[Developer] EFM Debug Indicator - Toggle`，原設定沒有預設快捷鍵。
使用既有綁定即可；未開啟畫面也會記錄 CSV。

| 畫面文字 | 意義 |
|---|---|
| `STORES OBS OK` / `STORES OBS REASON` | 掛載觀測有效性／原因，正常為 True／0 |
| `STORES SOURCE BATCH` | 原始掛載批次，任務持續運行時會增加 |
| `MC 01` 到 `MC 09` | 九站庫存：`P` 有掛載、`Q` 數量、分類／用途、`L` 掛載版本、`OK` 當前觀測有效 |
| `ID 01` 到 `ID 09` | MC 保存的四層類型及完整 CLSID |
| `IN 01` 到 `IN 09` | 經 Bridge 解析後送入 MC 的資料 |
| `ALL MISSILES` / `AA MISSILES` | 全部飛彈／空對空飛彈數量 |
| `ALL COUNT COMPLETE` / `AA COUNT COMPLETE` | 對應數量的分類資料完整性 |
| `GUN API OK` / `GUN API COUNT` | 現有彈量介面是否讀到有效值／回傳值 |
| `GUN MC COUNT` / `GUN REQUESTED` | MC 彈量／MC 已接受的射擊要求 |

原始 DCS 回傳另寫入 Saved Games 下的 `DCS/Logs/dcs.log`（使用 DCS.openbeta 時為該目錄）。
`FCK1C STORES` 記錄原始掛載 table，包括 weapon、wsType、adapter、container 及額外欄位；
`FCK1C STORES_COUNT` 記錄實際嘗試的數量 API，以及每秒一次的 `LoGetPayloadInfo` 可見性與回傳。
兩者在內容改變時寫入，原始掛載記錄附帶來源批次與重新掛彈版本。

## 1. 空掛載

進入任務後保持 5 秒。

看 `MC 01–09`：預期九站均無掛載、數量為 0；兩種飛彈總數均為 0。
`STORES OBS OK=True`、`STORES OBS REASON=0`，`STORES SOURCE BATCH` 持續增加。
空掛點的原生回傳型態由 dcs.log 一併保留，供判讀 P 的映射。

## 2. 混合掛載 A

按 **反斜線 `\`** 開啟通訊選單，再按 **F8（地勤）→ F1（重新裝填與加油）**。
依下表 A 欄選擇掛載，機砲保持 100%，按視窗的確認按鈕。
等待地勤完成，再保持 5 秒。

| 機型掛點／座艙索引 | 掛載 A | 之後的掛載 B |
|---|---|---|
| 1 RT／0 | AIM-9L，1 枚 | AIM-9P5，1 枚 |
| 2 RO／1 | Mk-82，1 枚 | 空 |
| 3 RI／2 | BRU-33 雙聯 Mk-82 | 275 gal 副油箱 |
| 4 MM／3 | 空 | Mk-82，1 枚 |
| 5 MF／4 | AIM-7E，1 枚 | 空 |
| 6 MB／5 | AIM-7F，1 枚 | 空 |
| 7 LI／6 | 275 gal 副油箱 | AIM-7M，1 枚 |
| 8 LO／7 | AN/ASQ-T50 ACMI 莢艙 | 維持同一莢艙 |
| 9 LT／8 | AIM-9P5，1 枚 | 空 |

MM 與 MF／MB 互斥，因此用 A、B 兩種配置涵蓋九個掛點。

看每一列的掛點與型號是否對上，尤其第 8、9 站；副油箱、炸彈、莢艙也應有獨立紀錄。
`ALL MISSILES=4`、`AA MISSILES=4`。雙聯掛架的原始 count、容器及子武器資訊會一併留下，
用來確認 DCS 數量代表幾枚武器或幾組掛架；MC 的數量應與該筆原始 count 一致。

## 3. 一次機砲點放

按 **右 Ctrl＋D** 進入 DGFT，按住 **Space 約 1 秒**後放開，保持 5 秒。
確認有槍口火光或射擊聲；觀察 `GUN API OK`、`GUN API COUNT` 與 `GUN MC COUNT`。
再按 **1** 回 NAV、按 **右 Shift＋M** 關閉主保險。

判讀依據：

- `GUN API OK=True`：原始數字應隨實際射擊下降，放開後保持，MC 彈量應跟隨。
- `GUN API OK=False`：現有候選沒有提供有效彈量；MC 的下降屬估算。日誌會列出每個實際嘗試的原因。
- `LoGetPayloadInfo` 若可在座艙呼叫，日誌同時保存 `Cannon.shells`，供比較射擊前後及重新掛彈後的實際變化。

這一步確認資料來源與語意，不要求你計算實際打出幾發。若沒有實際射擊，回報「未出彈」。

## 4. 改為掛載 B，再清空

再次按 **`\` → F8 → F1**，依表格 B 欄換掛，機砲補回 100%。
等待完成，再保持 5 秒。

看 MM 新掛載、MF／MB 清空、RI／LI 更換類型、RT 更換型號、LT 清空；LO 維持相同莢艙。
`ALL MISSILES=2`、`AA MISSILES=2`。重新掛彈版本應前進，庫存應反映 B；
若原生機砲來源有效，其數量應恢復至本機型設定的 523 發。

最後按 **`\` → F8 → F1**，清空全部九掛點；等待完成，再保持 5 秒。
預期九站恢復無掛載與零數量，兩種飛彈總數回到 0，舊型號不再視為目前掛載。

## 回傳

按 **Esc**，選擇結束任務。保留此次 DCS 版本與下列檔案：

1. 安裝模組內的 `log/debug.csv`。
2. Saved Games 對應 DCS 目錄下的 `Logs/dcs.log`。
3. 開始時保存的 `.miz`。A／B 若依表操作，無須另抄掛載表；選項缺少或換用其他項目時，告訴我掛點與替代品。

回報只需：`1 空掛載：正常／異常；2 A：正常／異常；3 機砲：出彈／未出彈；4 B及清空：正常／異常`。
異常補一句看到什麼即可，具體欄位與資料流程由記錄分析。

本次只驗證觀測與庫存傳遞。導彈發射、導引、模式完整驗收與故障注入另行安排。
目前可選的標準掛載作為介面代表；未在本地找到註冊來源的 HF-3／TC 系列，不列為這輪人工測試前提。

## 判讀規則

| 結果 | 依據 |
|---|---|
| 原生讀取成功 | call_ok=true，回傳含掛載資料；批次有前進 |
| 原生空站語意 | 由空掛載階段比對 nil／table、CLSID、count、weapon 與 wsType |
| 傳遞正確 | 原始 DCS 值 → IN → MC 的掛點、識別及數量一致 |
| 分類問題 | 原生資料存在，但 MC 顯示 UNKNOWN 或數量完整性為 False |
| 掛點映射問題 | A／B 的不同型號出現在錯誤站位 |
| 更新問題 | 原始回傳已改變，MC 仍保留前一個有效掛載 |
| 現有機砲介面不可用 | 所有實際候選缺少、呼叫失敗或回傳值未通過數值檢查 |
| 可採用的機砲來源 | 具體原生欄位隨射擊下降、停止後保持、重新掛彈恢復 |

穩態欄位由 5 秒記錄判讀；CSV 序號有缺口時標示缺少的區間，不以取樣檔推定完整事件順序。
結論逐項列出通過／失敗／資料來源結果與對應時間，適用本次測到的掛載配置與操作。
